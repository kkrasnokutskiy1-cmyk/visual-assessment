# Банк асессмента

Первая версия `visual-foundations` — 24 задания в шести блоках. Она предназначена для формирования гипотез при последующем качественном разборе, а не для автоматического определения уровня или подсчёта рейтинга. Продолжительность и диагностическую способность нужно проверить на реальном прохождении; заявлять, что набор рассчитан на несколько сеансов по 30–60 минут, пока нельзя.

Все изображения в `public/assessment-assets/` — специально созданные для этого проекта схематичные SVG. Это искусственные учебные примеры, а не доказательство качества реальных продуктов. Изображения фиксированы независимо от темы платформы. Названия счетов и суммы в них вымышлены. Для тонкой оценки типографики браузерные шрифты и масштабирование могут менять восприятие: примеры стоит проверить на целевом экране перед использованием результатов для выводов.

## Новые материалы и чтение

Для новых заданий используйте реальные опубликованные кейсы с доступным первоисточником и указанием автора. Разделяйте то, что утверждает автор, и собственную интерпретацию; не приписывайте решению измеренный эффект, если источник его не приводит. Самостоятельно нарисованные примеры и вопросы без визуального материала не соответствуют новой постановке задачи. До публикации стороннего изображения необходимо проверить право его воспроизведения: ссылка на автора сама по себе не является лицензией.

Приоритет источников для нового банка: опубликованные решения и руководства самих продуктовых команд (например, Apple HIG, Material Design, Figma, Linear, Stripe), где можно проверить дату, контекст и конкретный визуальный материал. Исторические работы допустимы как фундамент, если вопрос прямо проверяет перенос принципа в современный интерфейс. Не используйте старый интерфейс или вторичный пересказ как единственное доказательство актуального паттерна. HIG описывает рекомендуемое поведение платформы; это не измеренный эффект продукта. Если источник не содержит результата исследования, формулируйте вопрос как выбор и аргументацию решения для сценария.

Для глубины асессмента проверяйте матрицу «тема × навык × тип решения»: типографика, композиция, цвет, иконография, плотные данные, навигация, состояния и обратная связь, переходы и ошибки. В каждом разделе нужны разные задачи, а не несколько вариантов одного факта. Указывайте роль пользователя, цель, частоту действия и цену ошибки там, где это влияет на выбор паттерна. Короткий вариант ответа должен выражать одно решение; детали кейса и ограничения размещайте в контексте и разборе после прохождения.

После завершения новой версии страница результатов может предложить список первоисточников по темам. Пропуски и ответы «не уверен» влияют только на порядок тем; это не оценка компетенций. Список чтения не является персональной программой: для неё нужен отдельный качественный разбор ответов и целей.

## Добавление версии

1. Сохранить существующий объект и его изображения без изменений: завершённые попытки ссылаются на идентификатор и версию набора и вопросов.
2. Добавить новый объект `Assessment` с тем же `id` и новой `version` в реестр `versions`; при изменении вопроса изменить его версию. Новые изображения сохранять под новыми именами.
3. Для каждого задания указать навык, контекст, источник и лицензию, а также наблюдение, возможные объяснения и допустимые альтернативы. Не выдавать предпочтение за универсально правильный ответ.
4. Проверить уникальность ID, существование изображений и корректность ссылок, читаемость на целевом размере, неоднозначность формулировок и несколько независимых наблюдений на каждый навык. Доступность и права на сторонние материалы необходимо подтвердить до их добавления.

Перед публикацией последовательно проверьте `node scripts/check-assessment.cjs`, `npm run lint` и `npm run build`, затем вручную пройдите вопросы на узком и широком экранах. Для каждого вопроса проверьте, что варианты не накладываются, текст не обрезается, изображения различимы в масштабе интерфейса, а ссылка действительно подтверждает заявленное наблюдение. После публикации откройте пользовательский маршрут в production и убедитесь, что он отдаёт новую версию; успешная сборка сама по себе этого не подтверждает.

`getAssessment(id, version)` возвращает конкретную сохранённую версию; без версии — последнюю. Потребители результатов и возобновления должны передавать сохранённую версию попытки. Для клиентских компонентов используйте `PublicAssessment` и серверные функции из `lib/assessment/public.ts`: они исключают критерии интерпретации. Не импортируйте полный банк в клиентские компоненты: это добавит критерии в клиентский пакет, даже если они не отображаются в интерфейсе. При добавлении или изменении маршрутов проверяйте отсутствие таких импортов.
